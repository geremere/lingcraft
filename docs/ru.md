## Имеет ли смысл ваша модель?

**Да, с одним важным уточнением:** для лексики и грамматики должны действовать **разные правила продвижения** — ваш инстинкт педагогически обоснован.

| Измерение | Лексика | Грамматика |
|-----------|---------|------------|
| Единица освоения | Лемма/значение (`vocabulary_word`) | Тема (`grammar_block`) |
| Продвижение по уровню | `level_progress` ≥ 70% слов с R≥0.90 | **Ниже порог:** все темы показаны + avg R ≥ ~0.35 (см. раздел о грамматике) |
| Выбор в викторине | Очередь приоритетов в рамках S=7 | **Все K=3 слота из полного пула тем** — P(topic) ∝ низкий R + due + сложность |
| Роль частотности | **Порядок** внутри уровня (сначала частые слова) | Порядок в учебной программе (`sort_order`) |
| FSRS применяется к | Слову/значению | Грамматической теме (не отдельным предложениям) |

**Межъязыковая лексика (подтверждено):** каждая строка в `vocabulary_words` — независимая единица обучения со **собственным** `level_id` и `frequency_rank`. `word_links` связывают переводные эквиваленты между языками, но **не синхронизируют и не наследуют** уровень CEFR.

[Диаграмма — см. исходный markdown или рендерер Mermaid]

Пример — одно понятие, разные уровни:

| Строка слова | Язык | Лемма | level_id | Почему различается |
|--------------|------|-------|----------|-------------------|
| 101 | EN | bank | B1 | финансовое значение, реже |
| 205 | RU | банк | A1 | когнат, высокая частотность в программе RU |
| 102 | EN | run | A0 | базовый глагол |
| 310 | ES | correr | A1 | не когнат для большинства учеников |

**Правила:**
- FSRS `review_items` отслеживает каждую строку слова независимо (пользователь, изучающий EN, имеет отдельные карточки от пользователя, изучающего ES).
- `word_links` используется только в UI (popover перевода, подсказки) — никогда для продвижения по уровню или расчёта покрытия.
- Частотный ранг определяет **какое слово ввести следующим** в рамках `(language, level)` — а не к какому уровню относится слово.
- При импорте переводов задавайте `level_id` для каждого языка по учебной программе/частотным данным этого языка; не копируйте из связанного слова.

Это соответствует текущей схеме: [`vocabulary_words.level_id`](back/migrations/0001_init.up.sql) + [`word_links`](back/migrations/0003_word_graph.up.sql) без общей таблицы понятий.

## Проектное решение: уверенность только из FSRS

**Все значения «уверенности» вычисляются алгоритмом FSRS — без пользовательских оценок освоения, без отдельных счётчиков точности.**

Каждая строка `review_items` хранит состояние карточки FSRS (`stability`, `difficulty`, `elapsed_days`, `state`, `due`, …). В любой момент **retrievability** (доступность из памяти) выводится так:

```
R(item, now) = FSRS.ForgettingCurve(elapsed_days, stability)
             = (1 + factor * elapsed_days / stability) ^ decay   // стиль FSRS-4
             = exp(ln(0.9) * elapsed_days / stability)           // распространённое приближение
```

Используйте ту же функцию из `go-fsrs/v3`, что управляет планированием (уже обёрнута в [`fsrsx`](back/internal/fsrsx/fsrsx.go)).

| Сценарий использования | Метрика на основе FSRS |
|------------------------|------------------------|
| Уверенность по элементу (слово или грамматическая тема) | `R(item, now)` |
| Модальность задания (MCQ vs свободный ответ) | `R(item, now) >= 0.50` |
| Прогресс по уровню лексики | `mastered_count(L) / CURRICULUM_SIZE(L)`, где mastered = R ≥ 0.90 |
| Готовность грамматического уровня | avg R ≥ 0.35 + все темы показаны хотя бы раз | Ниже порог продвижения, чем у лексики |
| Выбор грамматического слота | P(topic) ∝ (1 − R) среди **всех** тем программы | Всегда в ротации, не исключаются |
| P(новый элемент) | `headroom × confidence_gate(avg_R)` — динамически, на основе FSRS |
| Приоритет элемента викторины (сначала due) | `due <= now` из той же карточки FSRS |

**Чем уверенность FSRS НЕ является:** скоростью ответа, сырой долей правильных ответов или пользовательским флагом «я это знаю». Они могут подавать **рейтинги** FSRS при отправке ответа (как сейчас), но уверенность для отображения и планирования — всегда `R`.

## Базовые понятия (три слоя, все на FSRS)

[Диаграмма — см. исходный markdown или рендерер Mermaid]

1. **Уверенность по элементу** — `R(item)` из карточки FSRS. Управляет планированием, **модальностью задания** и выборкой сложности предложений.
2. **Метрики уровня** — фиксированные размеры программы на уровень CEFR (например, 100 слов A0 = готовность к A1). Прогресс = число слов/тем выше порога уверенности FSRS. Управляет продвижением по уровню.
3. **Вероятность нового элемента** — динамически на сессию, из avg FSRS confidence + запаса программы. Низкая уверенность → сначала укрепление, потом новые элементы (лексика и грамматика).
4. **Сложность предложения** — вероятностный выбор уровня примерного предложения с весами по прогрессу уровня.

## UML сущностей (целевое состояние)

[Диаграмма — см. исходный markdown или рендерер Mermaid]

### Модель контента: exemplars + exercises (заменяет `tasks` как драйвер викторины)

**`tasks` устарела как единица викторины.** Сборка викторины в runtime выбирает **review item** (слово или грамматическую тему), затем **exemplar-предложение**, затем подходящее **заранее созданное упражнение**. DTO викторины собирается при запросе.

| Сущность | Роль | FSRS? |
|----------|------|-------|
| `ReviewItem` | Карточка FSRS на слово или grammar_block | Да — единственная единица планирования |
| `WordSentenceExemplar` / `GrammarBlockExample` | Элемент ↔ предложение с `sort_order`; в будущем `quality_tier` | Да |
| `UserExemplarCompletion` | Отслеживает просмотренные предложения на user+тему для ротации | Да |
| `Exercise` | Заранее созданный drill на предложении (индекс пропуска, правильный ответ) | Нет — артефакт контента |
| `ExerciseDistractor` | Заранее созданные неверные ответы для MCQ — **никогда не генерируются на лету** | Нет |
| `QuizSessionItem` | Runtime DTO: `{review_item, exercise, presentation_mode}` | N/A |

[Диаграмма — см. исходный markdown или рендерер Mermaid]

**Миграция с текущей схемы:** переименовать/эволюционировать [`tasks`](back/migrations/0001_init.up.sql) → `exercises`, [`task_distractors`](back/migrations/0001_init.up.sql) → `exercise_distractors`, [`task_vocabulary_words`](back/migrations/0001_init.up.sql) / [`task_grammar_blocks`](back/migrations/0001_init.up.sql) → `exercises.primary_word_id` / `exercises.primary_grammar_block_id`. [`task_attempts`](back/migrations/0001_init.up.sql) ссылается на `exercise_id`.

#### Тегирование грамматики на упражнениях

**MVP:** один `primary_grammar_block_id` на упражнение — управляет обновлением FSRS при отправке и выбором в викторине.

**Будущее / сырая концепция — multi-grammar tags (если получится):**

Некоторые предложения действительно проверяют несколько правил сразу. Может понадобиться пометить упражнение несколькими grammar blocks без полноценного multi-card FSRS.

```
exercises.primary_grammar_block_id   -- MVP: единственная цель FSRS при submit
exercise_grammar_tags                -- будущая junction: (exercise_id, grammar_block_id, role)
  role: 'primary' | 'secondary' | 'illustrative'
```

| Фаза | Поведение |
|------|-----------|
| MVP | Только один primary; junction-таблица игнорируется |
| Future v1 | Secondary-теги для обзора программы, «связанных тем», статистики — **без FSRS** |
| Future v2 (raw) | При submit обновлять FSRS для primary; опционально небольшой boost рейтинга secondary-тегам — **нужен дизайн** |

Открытые вопросы при multi-tag FSRS: делить рейтинг между карточками? обновлять только primary? требовать от пользователя указать, какое правило он применил?

Не планируется для MVP — только крючок в схеме (зарезервирована таблица `exercise_grammar_tags`), чтобы не загнать себя в угол.

#### Distractors: только заранее созданные

Неверные ответы MCQ должны быть **сгенерированы офлайн и проверены** (текущие `taskgen`, `vocabtaskgen.py`, seeds). Сборка в runtime выбирает существующее `Exercise` + его distractors; **не** вызывает LLM и не подбирает случайную лемму при запросе. Контроль качества при импорте.

Для режима `free_recall` distractors не используются; оценка по `correct_answer` + правилам нормализации.

То же для лексики: один `primary_word_id` на упражнение (multi-word tagging — та же сырая схема на будущее при необходимости).

## Продвижение по уровням лексики

### Обзор исследований (что говорит литература)

**CEFR не задаёт официальных подсчётов словарного запаса.** Рамка описывает коммуникативную способность, а не фиксированный список слов. Все числа ниже — оценки исследований, а не требования CEFR.

#### Эмпирический размер словаря по уровням CEFR (Milton & Alexiou 2009)

Рецептивный словарь учащихся, сдавших экзамены уровня ([источник](https://ikindalikelanguages.com/blog/common-european-languages-framework-cefrand-vocabulary-size/)):

| CEFR | Английский (рецептивные леммы, накопительно) |
|------|---------------------------------------------|
| A1 | < 1 500 |
| A2 | 1 500 – 2 500 |
| B1 | 2 750 – 3 250 |
| B2 | 3 250 – 3 750 |
| C1 | 3 750 – 4 500 |
| C2 | 4 500 – 5 000 |

Важно: это **накопительные итоги** у тех, кто уже сдал экзамены — не инкрементальные размеры программы. Индивидуальная вариативность велика; резкого порога нет (Schmitt et al. 2011).

#### Списки программ Совета Европы (Van Ek & Trim)

Исторические спецификации, повлиявшие на обучение по CEFR:

| Спецификация | Соответствует | Прибл. размер списка |
|--------------|---------------|----------------------|
| Waystage 1990 | ~A2 | ~1 000 слов |
| Threshold Level 1990 | ~B1 | ~2 000 слов |

#### Частотные списки и покрытие текста (Nation 2006, NGSL)

Размер словаря vs покрытие текста (английские **word families**):

| Известных слов | Покрытие текста | Следствие |
|----------------|-----------------|-----------|
| 1 000 | ~78–81% | Трудно читать; много незнакомого |
| 2 000 | ~87% | Всё ещё сложно |
| 3 000 | ~90% | Минимум для обучения из контекста |
| 5 000 | ~95% | Достаточное понимание (Laufer 1989) |
| 8 000–9 000 | ~98% | Комфортное самостоятельное чтение (Hu & Nation 2000) |

[NGSL](https://www.newgeneralservicelist.org/) (~2 809 лемм) даёт ~92% покрытия общего английского. Часто делят на **5 полос по ~560 слов** для поэтапного обучения. Первые 1 000 слов NGSL сами покрывают ~98% на некоторых ограниченных экзаменах.

#### Пороги comprehensible input (i+1)

Чтобы входной материал был обучаемым без перегрузки:

| % известных слов в тексте | Эффект |
|---------------------------|--------|
| < 90% | Понимание резко падает; усвоение останавливается |
| 95% | Достаточное понимание (Laufer 1989) — ~1 незнакомое на 20 слов |
| 98% | Комфортное чтение без помощи (Hu & Nation 2000, Schmitt 2011) |

**Следствие для дизайна:** вводить новые слова только когда активный словарь ученика на этом уровне достаточно силён, чтобы предложения викторины оставались на ~90–95% известными. Это поддерживает `confidence_gate` и `R_FLOOR` в P(new).

#### Устойчивая скорость новых слов (SRS-практика)

| Источник | Рекомендация |
|----------|--------------|
| Anki / сообщество FSRS | 10–20 новых карточек/день; desired retention 0.90 |
| StudyThai / общая SLA | 5–10/день для начинающих; 10–15 в месяцы 1–3; нагрузка повторений быстро растёт |
| Правило большого пальца | Каждое новое слово → ~5+ будущих повторений за 30 дней |

При викторине Lingraft N=10 (**S=7, K=3**) **1–2 новых слова за сессию** устойчивы, если пользователь проходит одну викторину в день — согласуется с исследованиями.

#### A0 — нестандартный уровень

Официальный CEFR начинается с A1. **A0** — полоса до A1 в приложениях для абсолютных новичков (выживание, топ частотности). Нет консенсуса по размеру A0; **100–300 слов** — разумная веха приложения перед формальным контентом A1.

### Проектные решения на основе исследований

| Решение | Исследовательская база | Выбор Lingraft |
|---------|------------------------|----------------|
| Фиксированная программа на уровень | Waystage/Threshold с определёнными списками; NGSL — полосы по 560 слов | Таблица конфигурации `LevelCurriculum` |
| Считать леммы/значения, не строки БД | Milton, Nation — подсчёт лемм/word families | Строки sense в `vocabulary_words`, порядок по `frequency_rank` |
| Mastered = R ≥ 0.90 | FSRS default desired retention; 98% Nation требует высокой stability | `MASTERED_THRESHOLD = 0.90` |
| Разблокировка L+1 при ~70% прогресса уровня | i+1 input: ~70–80% известного словаря в материале | `LEVEL_UNLOCK_THRESHOLD = 0.70` |
| P(new) падает по мере заполнения программы | Накопление нагрузки SRS; comprehensible input | формула `headroom` |
| P(new) = 0 при низком avg_R | Ниже 90% известного → коллапс понимания | `R_FLOOR = 0.40` |
| Макс. ~2 новых слова/викторина cold start | 10–20 новых/день устойчиво | `MAX_NEW_PER_QUIZ = 2` |
| Программа на язык | Milton: требования к словарю различаются по языкам | `LevelCurriculum(language_id, level_id)` |

### Рекомендуемые константы `LevelCurriculum` (подтверждено)

**Статус: согласовано.** Инкрементальное число слов для освоения на уровень — слова с тегом `level_id = L`, порядок по `frequency_rank`. Расширить A0 к полосе NGSL 560 слов после MVP при необходимости.

| Уровень | Слов (инкремент) | Грамматических тем (инкремент) | Примечания |
|---------|------------------|--------------------------------|------------|
| **A0** | **100** | **10** | Меньше тем; каждая выбирается по приоритету FSRS в K=3 |
| **A1** | **400** | **~15** | |
| **A2** | **500** | **~20** | |
| **B1** | **1 000** | **~25** | |
| **B2** | **1 500** | **~30** | |
| **C1** | **1 000** | **~20** | |
| **C2** | **500+** | **~15** | |

```
VOCAB_CURRICULUM(L)    = top N слов по frequency_rank на уровне L
GRAMMAR_CURRICULUM(L)  = grammar_blocks на уровне L с exemplar+exercise, по sort_order
```

### Состояния слова (на основе FSRS)

```
R(w) = 0                         если нет review_item
R(w) = FSRS.ForgettingCurve(now) иначе

mastered(w) = R(w) >= MASTERED_THRESHOLD   // 0.90 — согласовано с FSRS desired retention
touched(w)  = review_item существует
new(w)      = not touched(w)
```

### Прогресс уровня (что видит пользователь)

```
mastered_count(L) = count(w in CURRICULUM(L) where mastered(w))
level_progress(L) = mastered_count(L) / LevelCurriculum.target_word_count(L)
```

Пример: 73 из 100 слов A0 с R ≥ 0.90 → **прогресс A0 = 73%**.

### Правила продвижения по уровню (с опорой на исследования)

```
# Мягкая разблокировка — начать видеть слова L+1 в викторине
level_progress(L) >= 0.70          // ~70% программы стабильно; диапазон i+1 input

# Жёсткая разблокировка — обновить current_level_id
level_progress(vocab, L) >= 0.70
AND grammar_exposure(L)           # все грамматические темы показаны хотя бы раз
AND grammar_avg_R(L) >= 0.35      # ниже, чем у лексики — постоянное повторение ожидается

# Полное завершение уровня (значок)
level_progress(L) >= 1.0           // все слова программы с R >= 0.90
```

Подмешивание L+1 до 100% завершения поддерживается исследованиями i+1 (Nation, Krashen) — ожидание 100% вызывает скуку; 70% — разумный старт смешивания.

### Соответствие исследований константам (подтверждено)

| Константа | Лексика | Грамматика | Статус |
|-----------|---------|------------|--------|
| `MASTERED_THRESHOLD` | 0.90 | **0.55** | «Знаю» по грамматике — ниже порог |
| `LEVEL_UNLOCK_THRESHOLD` | 0.70 (число слов) | **avg R ≥ 0.35** + все темы показаны | Подтверждено |
| `R_FLOOR` | 0.40 | **0.30** | Подтверждено |
| `R_TARGET` | 0.70 | 0.60 | Подтверждено |
| `R_STRENGTHEN` | 0.50 | **0.35** | Подтверждено |
| `MAX_NEW_PER_QUIZ` | 2 | **1** | Подтверждено |
| `MAX_DUE_PER_QUIZ` | 5 | **2** | Подтверждено |
| `MIN_WEAK_SLOTS` | 2 | **1** | Подтверждено |
| `MIN_NEW_SLOTS` | 1 | 0–1 | Подтверждено |
| `BACKLOG_WARN` | 50 | **15** | Подтверждено |
| `BACKLOG_CRITICAL` | 200 | **30** | Подтверждено |
| `MIN_DATA_TOUCHED` | 10 | 3 темы | Подтверждено |

**Смесь викторины (MVP — фиксированная, не из соотношения):**

| Константа | Значение | Обоснование |
|-----------|----------|-------------|
| `N` | 10 | Размер сессии |
| `S` (слоты лексики) | **7** | Изучение языка в основном лексика; занимает больше времени |
| `K` (слоты грамматики) | **3** | Меньшая программа; 3 слота достаточно, чтобы FSRS выразил приоритет |

Будущий вариант: выводить S/K из соотношения размеров программ — **отложено**, не MVP.

## Очередь приоритетов и контроль backlog

### Проблема

Чистое планирование FSRS имеет два режима отказа:

1. **Лавина повторений** — пользователь пропускает дни или введено слишком много нового → 1 000 элементов `due <= now` → невозможно завершить, пользователь уходит.
2. **Ад повторений** — «сначала все due» навсегда голодит новые слова при большом backlog.

FSRS сам задаёт **когда** элементы становятся due; он не ограничивает **сколько** попадает в сессию. Lingraft нужна **очередь приоритетов на уровне сессии** поверх FSRS.

### Дизайн: очередь приоритетов с бюджетами слотов

Каждая викторина собирает ровно **N = 10 элементов** из пула кандидатов с оценкой — не больше, независимо от числа due.

[Диаграмма — см. исходный markdown или рендерер Mermaid]

#### Оценка приоритета (выше = выше шанс выбора)

```
overdue_days = max(0, days since due)

priority(item) =
  if R < R_STRENGTHEN:
      1000 + (R_STRENGTHEN - R) * 200        // слабые элементы доминируют
  elif due <= now:
      500 + overdue_days * 10                 // due; чем старше просрочка, тем выше
  elif is_new and confidence_gate > 0:
      100 + (1 - level_headroom) * 50         // новые могут обогнать «застоявшиеся» повторения
  else:
      R * 50                                  // filler: non-due повторения с низким R
```

**Слабые элементы (R < R_STRENGTHEN) всегда обгоняют due**, если оба есть — соответствует «сначала укрепление, потом расширение» и требованию гораздо большей вероятности для элементов с низкой уверенностью.

#### Разделение слотов — фиксированное 7:3 (MVP)

**Допущение:** изучение языка **в основном лексика**, и лексика занимает **гораздо больше времени**, чем грамматика. Грамматических тем меньше, они абстрактнее; экспозиция на тему задаётся **какие темы выигрывают 3 грамматических слота**, а не уменьшением K под соотношение программ.

```
N = 10
S = 7   # слоты лексики — фиксировано для MVP
K = 3   # слоты грамматики — фиксировано для MVP
```

Внутри S и K **тот же алгоритм очереди приоритетов** применяется независимо к каждому виду. Уверенность FSRS (`R`, due date, пороги слабости) определяет **какие слова/темы появляются** — а не сколько слотов у каждого вида.

**Какие грамматические темы в 3 слотах:** взвешенная выборка из **всех** тем `GRAMMAR_CURRICULUM` — `P(t) ∝ (1 - R(t))` + due boost. Низкая уверенность → высокая вероятность; высокая — всё равно появляется, просто реже. Одна тема может повториться, если вес доминирует.

**Будущее (отложено):** динамический `S/K` из `grammar_topics / (vocab_words + grammar_topics)` — может иметь смысл позже; не для MVP.

#### Константы по виду (при фиксированных S=7 / K=3)

| Параметр | Лексика (S=7) | Грамматика (K=3) | Почему различается |
|----------|---------------|------------------|-------------------|
| `R_STRENGTHEN` | 0.50 | **0.35** | Вес в `(1-R)`; не жёсткое исключение |
| `GRAMMAR_PROMOTION_R` | — | **0.35** | avg R для разблокировки L+1 по грамматике |
| `MASTERED_THRESHOLD` | 0.90 | **0.55** | Отображение «известная тема» |
| `R_FLOOR` (блок новых) | 0.40 | **0.30** | Строже ворота перед новыми темами |
| `MIN_WEAK_SLOTS` | 2 | **1** | Резерв слотов для слабых в бюджете вида |
| `MIN_NEW_SLOTS` | 1 | **0–1** | Не более 1 новой грамматической темы за викторину |
| `MAX_NEW_PER_QUIZ` | 2 | **1** | Меньшая грамматическая программа |
| `MAX_DUE_PER_QUIZ` | 5 | **3** | Можно заполнить все K слота, если все due |
| `BACKLOG_WARN` | 50 | **15** | |
| `BACKLOG_CRITICAL` | 200 | **30** | |

#### Грамматическая уверенность растёт медленнее (в рамках K=3)

Грамматика **не лексика**. Меньше тем, сложнее exemplars (прогрессия сложности предложений), понятия требуют **пожизненной ротации** — не одноразового освоения.

**Идея:** пользователь должен **всегда видеть все грамматические темы в пуле**, с **вероятностью пропорциональной потребности** (низкий R → высокая вероятность), а не блокироваться до «достаточно сильного» состояния.

```
# Вес выбора для грамматической темы t (все темы GRAMMAR_CURRICULUM всегда eligible)
need(t)     = 1 - R(t)                          // низкая уверенность → высокая потребность
due_boost(t)= overdue_days * 0.1 if due <= now else 0
complexity  = exposure_factor from sentence level sampling  // сложнее примеры → чаще revisiting

weight(t)   = need(t) + due_boost(t) + complexity
P(select t) = weight(t) / sum(weight(all topics at level L))
```

Выбрать K=3 темы **взвешенной выборкой без возвращения** (или очередью приоритетов с теми же весами). Тема с R=0.80 всё равно иногда появляется; при R=0.15 доминирует.

**Почему ниже пороги продвижения:**

| | Лексика | Грамматика |
|--|---------|------------|
| `MASTERED_THRESHOLD` | 0.90 | **0.55** — «достаточно хорошо» для перехода |
| Разблокировка уровня | 70% слов mastered | **avg R ≥ 0.35** по всем темам L + каждая показана ≥ раз |
| Философия | Нужно накопить сотни стабильных лемм | Нужно **коснуться каждого правила**; освоение продолжается через более сложные предложения |

Продвижение по грамматике **не** требует R≥0.90 по каждой теме. Пользователь разблокирует грамматику L+1, когда каждая тема A0 была показана и средняя уверенность скромная — потому что более сложные exemplars и ротация K=3 всё равно будут возвращать темы L0.

**Более сложные примеры = постоянное повторение:** даже «сильные» темы (R=0.70) получают предложения A1/A2 через прогрессию сложности → ошибки сбрасывают FSRS → тема остаётся в ротации. Грамматика никогда не «закончена».

**vs блокировка лексики при слабости:** грамматика **не** использует `P(new_grammar)=0`, пока есть слабые темы. Новые темы L+1 могут появляться как **подмешивание**, когда разрешает разблокировка лексики, с низким весом при плохом avg R текущего уровня. Темы текущего уровня всегда конкурируют в одном пуле.

**Фиксированное K=3** — какие 3 из 10 тем: взвешено по `(1-R)`, а не «только 3 разных слабых».

```
select_slots(kind, slot_count):   # slot_count = S=7 or K=3
  1. Build candidate pool for kind (vocab or grammar)
  2. Apply backlog-adjusted budgets (kind-specific constants)
  3. Reserve MIN_WEAK_SLOTS from highest-priority weak items
     → same item can be picked twice if still highest priority after dedupe? 
     → YES: allow repeat if R << others (dedupe only within same slot pass if R gap > threshold)
  4. Reserve MIN_NEW_SLOTS (if backlog healthy)
  5. Fill up to MAX_DUE_PER_QUIZ from due pool
  6. Fill remaining by priority_score descending
  7. For each picked review_item:
       pick exemplar sentence (level sampling)
       pick matching Exercise (pre-authored) for sentence + item
       set TaskPresentationMode from R_item
```

**Повтор той же темы в одной викторине:** разрешён, когда `priority(item) > 2 × second_best` — например, present-simple при R=0.10, остальные все R>0.60. Лимит повторов: `ceil(slot_count / 2)`, чтобы избежать марафона из 10 вопросов про present simple.

#### Backlog не растёт бесконечно (профилактика + восстановление)

| Механизм | Когда | Эффект |
|----------|-------|--------|
| `MAX_NEW_PER_QUIZ = 2` | всегда | ограничивает новые карточки, входящие в FSRS |
| `P(new) = headroom × confidence_gate` | всегда | снижает приток нового по мере заполнения программы или падения avg_R |
| `MIN_NEW = 0` when `due_backlog > 50` | восстановление | не добавлять, пока не разгрузят |
| `MAX_DUE_PER_QUIZ = 5` | норма | cap due за сессию; остальные ждут (остаются due) |
| `MAX_DUE = 7, MIN_NEW = 0` | `due_backlog > 200` | аварийный drain |
| Отложенные элементы сохраняют `due <= now` | всегда | конкурируют в следующей сессии по priority; без тихих потерь |

**Не выбран ≠ забыты.** Элементы остаются due и поднимаются в priority через `overdue_days`. Очередь — **priority queue**, а не FIFO-drain всех due.

#### Отслеживание backlog в snapshot

Расширить `UserLevelSnapshot`:

```
due_backlog_vocab    = count vocab review_items where due <= now
due_backlog_grammar  = count grammar review_items where due <= now
weak_count_vocab     = count where R < R_STRENGTHEN
avg_R_vocab          = avg R over touched curriculum words
```

Показывать в UI при `due_backlog > BACKLOG_WARN`: «У вас 73 повторения в очереди — новые слова приостановлены, пока не наверстаете.»

## Вероятность нового элемента (лексика + грамматика)

Базовый принцип: **сначала укрепление, потом расширение**. P(new) решает, попадают ли новые элементы в пул кандидатов; **очередь приоритетов** решает, выиграют ли они слоты у due/слабых.

### P(new) — ворота для новых элементов в пуле (оба вида)

Та же формула, константы и пороги backlog по виду (см. таблицу выше).

```
P(new) = 0                         if due_backlog_kind > BACKLOG_WARN_kind
       = headroom × confidence_gate otherwise
```

Грамматика: пул **всегда** включает **все** темы программы на уровне L. Новые темы L+1 подмешиваются только когда `level_progress` лексики позволяет; в пул с низким приоритетом. **Нет жёсткой блокировки** слабых тем — низкий R уже повышает вес выбора через `(1-R)`.

| Ситуация | Поведение |
|----------|-----------|
| Новый пользователь, < MIN_DATA touched | Статика: 2 слова A0 с weak-priority + макс. 2 новых |
| avg_R < R_FLOOR | Нет новых в пуле; заполняются MIN_WEAK_SLOTS |
| Здоровый A0, 1 грамматическая тема очень слабая | Тема может занять 2+ из K=3 слотов по priority |
| Хорошо по всей грамматике A0 (высокий avg R) | Все 10 тем всё ещё в пуле; темы с высоким R реже, но не нулевая вероятность |
| Низкий grammar avg_R | Темы с низким R доминируют K=3 через веса `(1-R)`; все темы остаются eligible |

## Продвижение по уровням грамматики

Грамматика использует **фиксированный набор тем на уровень** с **непрерывной ротацией** — все темы всегда в пуле викторины, выбор взвешен по `(1 - R)`.

```
GRAMMAR_CURRICULUM(L) = all grammar_blocks at level L with exemplar + exercise
mastered_topic(t)     = R(t) >= MASTERED_THRESHOLD_GRAMMAR   // 0.55, not 0.90
grammar_avg_R(L)      = avg(R(t)) over all t in GRAMMAR_CURRICULUM(L)
grammar_exposure(L)   = all t have reps >= 1
```

**Продвижение к контенту грамматики L+1** (ниже порог, чем у лексики):

```
level_progress(vocab, L) >= 0.70              // лексика всё ещё gating общего уровня
AND grammar_exposure(L) == true                 // каждая тема показана хотя бы раз
AND grammar_avg_R(L) >= GRAMMAR_PROMOTION_R   // напр. 0.35 — скромное среднее, не mastery
```

**Не требуется для продвижения:** каждая тема с R≥0.90 или пустой набор слабых. Более сложные exemplars обеспечивают повторение после продвижения.

**Выбор в викторине (в K=3):** взвешенная выборка из полного `GRAMMAR_CURRICULUM(L)` — вероятность ∝ `(1 - R(t))` + due boost. Одна тема может появиться дважды за викторину, если вес доминирует.

**Отображение прогресса:** `grammar_progress(L) = count(R >= 0.55) / count(topics)` для UI — только информационно; продвижение использует `grammar_avg_R` + exposure gate.

## Конвейер сборки викторины

[Диаграмма — см. исходный markdown или рендерер Mermaid]

**На каждый выбранный review item (лексика или грамматика):**

```
1. priority queue / weighted pick selects review_item
2. sample CEFR level L (complexity progression)
3. pick_exemplar(item, user, L) — rotation rules; no repeat until uniques exhausted
4. lookup Exercise WHERE sentence_id AND primary item match
5. TaskPresentationMode = f(R_item)
6. if mcq_4: attach pre-authored ExerciseDistractors
7. on submit: record user_exemplar_completions
8. emit QuizSessionItem
```

### Выборка уровня предложения (ваша формула, формализованная)

Для элемента `i` (слово или грамматическая тема) с mastery элемента `m = R(i)`:

```
P(level = L) ∝ user_level_weight(L) × exposure_factor(L, m)
```

Где:

- `user_level_weight(L)` = `level_progress(L)` из фиксированной программы (mastered_count / CURRICULUM_SIZE)
- `exposure_factor(L, m)` = усиление уровней **выше** tagged level элемента, когда `m` низкий (ваша идея прогрессии сложности)

Пример из вашего сценария:

- Пользователь: покрытие A0 80%, A1 30%
- Элемент G на A0, mastery 40%
- Нормализованные веса: A0=0.73, A1=0.27
- При низком mastery сдвиг 30% массы вероятности к A1 → ~51% предложение A0, ~49% A1 для этого элемента

**Fallback:** если нет exemplar на выбранном уровне — ближайший уровень с доступным предложением.

## Ротация exemplar-предложений (отдельная тема)

### Проблема

Exemplars связывают **слово или грамматическую тему** с **предложением**. Если одно и то же предложение повторяется, пользователь запоминает ответ **в фиксированном контексте** («я всегда blank третье слово в *Hello, my name is…*») вместо общего знания слова/правила.

**Правило:** для данной темы (слово или grammar block) **не повторять предложение**, пока пользователь не увидел все предыдущие exemplars в порядке ротации для этой темы на выбранных уровнях CEFR.

### Двухшаговый выбор (сначала уровень, потом предложение)

Выбор предложения — **два шага**; не смешивать с выборкой уровня выше:

```
1. Sample CEFR level L via P(level) ∝ user_level_weight × exposure_factor   (see above)
2. Pick concrete sentence via exemplar rotation rules below (this section)
```

### MVP: отслеживание завершений exemplar на пользователя

```
user_exemplar_completions (
  user_id,
  item_type,          -- vocabulary_word | grammar_block
  item_id,
  sentence_id,
  completed_at
)
UNIQUE (user_id, item_type, item_id, sentence_id)
```

При каждой отправке ответа викторины для `(item, sentence)` — записать completion.

**Порядок exemplars (MVP):** фиксированный `sort_order` на `WordSentenceExemplar` / `GrammarBlockExample` (порядок импорта или вручную). Пока без quality tiers.

#### MVP-алгоритм: `pick_exemplar(item, user, sampled_level L)`

```
candidates(L) = exemplars for item WHERE sentence.level_id = L
                ORDER BY sort_order ASC

unseen(L)     = candidates(L) WHERE sentence_id NOT IN user_exemplar_completions

if unseen(L) not empty:
    return first unseen(L) by sort_order          // исчерпать уникальные предложения на L
else:
    // все уникальные на L уже видены — НЕ сбрасывать и не выбирать случайный repeat
    next(L)     = candidates(L) WHERE sort_order > max seen sort_order at L
    if next(L) not empty:
        return first next(L)                      // «новый» exemplar добавлен после исчерпания uniques
    else:
        return pick by level sampling at L-1 or L+1 // переход на другие уровни
        // только если ВСЕ уровни исчерпаны: repeat самого давно виденного (last resort)
```

**Пользователь A0:** только предложения A0 для темы, пока каждый уникальный A0 exemplar не пройден раз, по `sort_order`.

**Пользователь A1:** сначала sample уровня — P(A0) vs P(A1) из правил прогрессии уровня — затем ротация **внутри выбранного уровня** как выше. Может видеть A0 или A1 для одной темы в разных викторинах, но не **то же** предложение дважды, пока uniques на этом уровне не исчерпаны.

**Когда uniques на уровне кончились:** предпочитать **новые exemplars** (больший `sort_order`, которого не было в БД при старте пользователя, или новые импортированные строки) — **никогда** сразу сбрасываться на случайные уже виденные на этом уровне.

[Диаграмма — см. исходный markdown или рендерер Mermaid]

### Будущее: quality tiers exemplars (не MVP)

Exemplars будут иметь **tier верификации**, задающий глобальный порядок предпочтения (до per-user ротации):

| Tier | Значение | Приоритет |
|------|----------|-----------|
| `human_verified` | Проверено человеком | 1 (показывать первым) |
| `ai_verified` | Проверено AI | 2 |
| `fast_review` | Лёгкий review pass | 3 |
| `human_authored_new` | Написано человеком, ещё не полностью проверено | 4 |
| `ai_generated_new` | Сгенерировано AI, ещё не полностью проверено | 5 |

```
ORDER BY quality_tier ASC, sort_order ASC
```

MVP использует только `sort_order`. В схеме можно зарезервировать nullable колонку `quality_tier` на будущее.

**Будущее поведение:** внутри одного tier те же правила ротации; uniques более высокого tier исчерпываются раньше нижнего; newly promoted tier (напр. AI → human_verified) входит в пул как «новый exemplar» без сброса seen set.

### Связь с прогрессией сложности

Более сложные уровни предложений (exemplar A1 для темы A0) взаимодействуют с ротацией:

- Выборка уровня решает **из какой полосы CEFR** брать.
- Ротация решает **какое уникальное предложение** внутри полосы.
- Должны пройти оба: пользователь получает i+1 сложность **и** свежий контекст.

Записывать `user_exemplar_completions` при каждой отправке независимо от правильности (отслеживание экспозиции) — опционально: только при правильном ответе, если «completed» = mastered in context (TBD; MVP = любая попытка).

**Режим представления решается на каждое задание при сборке викторины** по FSRS retrievability базового review item — не по прогрессу уровня, не по avg_R, не по сложности предложения.

Каждый **review item** (не строка exercise) задаёт presentation mode:

```
item  = vocabulary_word  OR grammar_block  (from ReviewItem)

R_item = FSRS.ForgettingCurve(review_items row)
       = 0 if no review_item yet
```

**Выбор режима (одно правило для лексики и грамматики):**

| Условие | TaskPresentationMode | Опыт пользователя |
|---------|---------------------|-------------------|
| `R_item < 0.50` | `mcq_4` | Выбор 1 из 4 |
| `R_item >= 0.50` | `free_recall` | Ввод правильного ответа |
| `R_item >= 0.85` (future) | `pronunciation` | Произнесение ответа |

```
presentation_mode(task) = mode_from_R(R_item)
```

**Гистерезис** (избежать flip-flop между викторинами):

```
switch to free_recall  when R_item >= 0.55
switch back to mcq_4   when R_item <  0.45
```

**Ключевые разделения:**

| Измерение | Задаётся |
|-----------|----------|
| TaskPresentationMode | **Этим** `R_item` |
| P(new word/topic) | avg_R + headroom по программе |
| CEFR-уровень предложения | R элемента + level_progress (прогрессия сложности) |
| FSRS rating при submit | правильность + скорость → обновление карточки → будущий R_item |

Задание по грамматике «present simple» и задание по слову «hello» получают свой режим независимо — низкий R слова → MCQ, даже если уверенность по грамматике высокая, и наоборот.

Текущий код выбирает заранее созданные [`tasks`](back/internal/handlers/quiz.go) как единицу викторины. Цель: `QuizPlanner` выбирает `ReviewItem` → exemplar → `Exercise`; mode вычисляется в runtime.

## Чёрные дыры и риски

| Риск | Почему больно | Смягчение |
|------|---------------|-----------|
| **Статические tasks vs runtime assembly** | Старая модель привязывает викторину к строке `tasks` | `ReviewItem` → exemplar → pre-authored `Exercise`; миграция таблицы `tasks` |
| Одно предложение повторяется для того же слова/темы | Запоминание контекста, а не общее обучение | `user_exemplar_completions` + ротация до repeat |
| Исчерпаны uniques → случайный repeat | Пользователь застревает в цикле | Предпочитать новые строки exemplar; соседний уровень; repeat только last resort |
| **Multi grammar tag на упражнение** | Сырая будущая концепция | MVP: только `primary_grammar_block_id`; зарезервировать junction `exercise_grammar_tags` |
| **Путаница FSRS rating и confidence** | Rating (again/hard/good/easy) — вход *в* FSRS при submit; confidence — выход `R` | Ratings обновляют карточку; всё планирование читает только `R` |
| **«Каждая тема» при разреженном контенте** | Если A0 — 40 blocks, но tasks только у 20, gate блокирует навсегда | Gate только по темам **с хотя бы одним exemplar/task** |
| **Массовый импорт слов без `level_id`** | Текущие импорты Kaikki передают level filter как NULL ([exploration finding]) | Backfill уровней или исключение из знаменателя покрытия |
| **FSRS rating vs mastery** | Текущий код выводит rating из speed+correctness, не из суждения пользователя ([`quiz.go`](back/internal/handlers/quiz.go)) | Auto-rating для MVP; модальность использует R, не rating |
| **Лавина повторений (1000+ due)** | Слишком много нового или пропущенные дни → пользователь уходит | Priority queue + `MAX_DUE_PER_QUIZ`; пауза новых при `BACKLOG_WARN`; emergency drain при 200 |
| **Ад повторений (никогда новых слов)** | Чистый «due first» голодит программу | `MIN_NEW_SLOTS = 1` при здоровом backlog |
| **Продвижение vs mix викторины** | Пользователь на потолке A1, но нужны повторения A0 | Слабые + due со всех уровней конкурируют по priority_score |
| **Голодание из-за очереди** | Будущая ручная очередь может вытеснить due | Cap очереди фиксированной quota; due заполняются первыми |
| **Оценка free recall** | Production по грамматике/лексике нужен fuzzy match, не exact string | План нормализации + таблица допустимых вариантов |
| **Дрейф знаменателя покрытия** | Добавление новых слов A0 позже снижает coverage всем | Версионировать наборы программы; snapshot знаменателя при unlock уровня |
